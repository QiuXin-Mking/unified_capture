## 背景

device-ui 需要通过 `/api/camera/preview` 获取 JPEG，但 unified_capture 只输出 H.265 MKV 和 Y8。已观察到在 TSTC SDK、MPP 初始化附近新增后台 pthread 会导致严重采集异常，因此预览不能通过新的进程内线程实现。

## 决策驱动因素

1. 不创建新的 pthread。
2. 不增加设备部署依赖，复用已链接的 libjpeg-turbo 2.0.6。
3. 预览不能持续占用采集循环，每次只按请求生成一帧。
4. 读取方不能看到未写完的 JPEG。
5. 5.5 英寸屏幕无需原始分辨率预览。

## 候选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 新线程消费共享帧队列 | 延迟低，职责分离 | 违反无新增 pthread 约束 |
| fork 子进程 + FIFO | 进程隔离 | 协议、缓冲和部署复杂 |
| 在 `collect()` 内按需同步生成 | 无新线程、复用已有 BGR、实现直接 | 单次请求增加采集循环耗时 |
| device-ui 独立打开 v4l2 | 与采集进程代码隔离 | 可能与 unified_capture 争用设备 |

## 决策

收到 `preview:<path>` 请求后，在现有 `VideoSensor::collect()` 或彩色 `SixCamSensor` 采集循环内同步完成 1/4 最近邻缩放、JPEG 压缩和原子文件替换；无请求时只检查原子标志。

## 理由

该方案不改变线程模型、不新增依赖，也不需要第二个进程争用摄像头。预览只在请求到来后的下一帧执行一次，额外成本受控，符合低频操作预览需求。

## 实施约束

- 使用原子 pending 标志和互斥保护目标路径，不创建新 pthread。
- 3840×1200 BGR 使用最近邻缩放为 960×300。
- JPEG 使用 `TJSAMP_420`、quality 85 和 `TJFLAG_FASTDCT`。
- `tjCompress2` 参数顺序固定为 width、pitch=0、height，兼容 libjpeg-turbo 2.0.6。
- 先写 `<path>.tmp`，成功后 `rename()` 到目标路径。
- 只有彩色通道生成预览；当前默认来源为第一个可用彩色摄像头。
- 预览 API 等待下一帧文件出现，不能把 Socket 命令成功等同于 JPEG 已落盘。

## 正面后果

- 保持生产采集线程模型不变。
- 无预览请求时只有一次原子标志快速检查。
- 复用已解码 BGR 和现有 libjpeg-turbo。
- 原子替换避免 device-ui 读取半截文件。

## 负面后果

- 生成预览的那一帧会同步增加缩放和压缩耗时。
- 当前只支持单一默认预览源。
- 最近邻缩放优先性能，画质低于双线性。

## 风险

| 风险 | 触发信号 | 缓解措施 |
|------|----------|----------|
| 同步编码导致掉帧 | 预览请求时采集帧率下降 | 监控单帧耗时；超限时回退子进程方案 |
| JPEG 参数与库版本不兼容 | `tjCompress2` 返回 -1 | 固定已实测的 TJSAMP_420 和参数顺序 |
| API 首帧 503 | 命令返回时文件尚未生成 | 后端以 20×50ms 短轮询等待 |

## 回退方案

若实机数据显示同步生成导致帧率或时序不达标，优先回退到 fork 子进程 + FIFO；若进程间方案仍不可接受，再评估由独立服务访问 v4l2，但必须先验证设备不会被争用。

## 验证方式

| 验证项 | 操作或指标 | 通过标准 | 状态 |
|--------|------------|----------|------|
| JPEG 输出 | 调用预览 API | HTTP 200，JPEG 为 960×300、约 30KB | 已通过 |
| 编码耗时 | 测量缩放和压缩 | 总增加耗时小于 10ms | 已通过 |
| 采集链路 | 预览期间录制 | 录制继续且无 TSTC/MPP 异常 | 已通过 |
