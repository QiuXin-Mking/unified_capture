# ADR 编写规则

本文件适用于 `docs/decisions/` 及其所有子目录。Codex 在本目录创建、提取、迁移、修改或审查 ADR 时，必须遵守以下规则。

## 创建前

1. 阅读本文件、`README.md` 和 `TEMPLATE.md`。
2. 搜索相同决策，避免重复：

   ```bash
   rg -n "<模块名|方案名|关键约束>" docs/decisions
   ```

3. 查阅相关 `docs/records/` 和 `docs/bugs/`，区分事实来源、故障证据和决策结论。
4. 只有当选择可以独立撤销、替换或重新评估时才新建 ADR。参数和实现细节应归入所属 ADR 的“实施约束”，不要拆成碎片化 ADR。

## 文件命名

- 实际 ADR 必须命名为 `YYYY-MM-DD-<slug>.md`。
- 日期使用决策被采纳或首次记录的日期。
- `<slug>` 使用小写英文和连字符。
- 不使用 `001-`、`002-` 等序号前缀。
- `README.md`、`TEMPLATE.md` 和 `AGENTS.md` 不受日期规则约束。

## 内容结构

以 `TEMPLATE.md` 为基础，不删除或调换以下二级标题：

1. `元数据`
2. `背景`
3. `决策驱动因素`
4. `候选方案`
5. `决策`
6. `理由`
7. `实施约束`
8. `正面后果`
9. `负面后果`
10. `风险`
11. `回退方案`
12. `验证方式`
13. `相关记录`
14. `变更记录`

## 决策边界与证据

- 每份 ADR 只表达一个核心决策。
- “背景”只写已知事实；未确认内容明确标注为推测。
- “候选方案”至少包含已采纳方案和一个真实考虑过的替代方案。
- “决策”必须是一句可执行、可验证的陈述。
- “理由”连接驱动因素与选择，避免只重复决策。
- “正面后果”和“负面后果”都必须填写。
- “回退方案”说明触发条件和恢复路径。
- “验证方式”给出命令、指标或可观察结果；尚未验证时明确写“未验证”。
- “相关记录”链接来源 record、Bug、计划或代码，不复制长篇证据。
- 修改已采纳 ADR 时追加“变更记录”；实质性反转应新建 ADR，并将旧 ADR 状态改为“已取代”。

## 从 Records 提取 ADR

当执行记录出现“决策”“选择”“采用”“拒绝”“保持兼容”等内容时：

1. 判断它是否具备独立决策边界。
2. 同一方案的参数、算法细节和原子写入方式合并在一份 ADR 中。
3. 创建日期命名的 ADR。
4. 在 ADR 的“相关记录”链接来源 record。
5. 在来源 record 顶部“提取的 ADR”添加反向链接。

## 完成前检查

```bash
for file in docs/decisions/20*.md; do
  basename "$file" | grep -Eq '^20[0-9]{2}-[0-9]{2}-[0-9]{2}-[a-z0-9]+(-[a-z0-9]+)*\.md$'
  for heading in "## 元数据" "## 背景" "## 决策驱动因素" "## 候选方案" \
    "## 决策" "## 理由" "## 实施约束" "## 正面后果" "## 负面后果" \
    "## 风险" "## 回退方案" "## 验证方式" "## 相关记录" "## 变更记录"; do
    grep -Fq "$heading" "$file" || {
      echo "缺少章节: $file -> $heading"
      exit 1
    }
  done
done
```

然后验证相对链接并执行 `git diff --check`。全部通过后才可声称 ADR 完成。
