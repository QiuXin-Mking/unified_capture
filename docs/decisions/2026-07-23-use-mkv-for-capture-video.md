## 背景

Rockchip MPP 直接输出裸 H.265 elementary stream，其中没有容器、时间戳索引或轨道元数据。统一采集程序需要将多路编码流经 FIFO 交给 FFmpeg 持续写盘，并在 GPIO 意外停止、进程崩溃或设备断电等非正常结束情形下，尽可能保留已录制的视频数据。

MP4 和 MKV 都可以封装 H.265。常规 MP4 在录制完成时才写入最终 `moov` 索引；若断流、断电或进程崩溃发生在此前，文件无法直接使用。MKV 按 Cluster 流式写入，异常停止后即使文件未完整收尾，已写入的 Cluster 仍可被读取和播放。因此，MKV 更适合长时间嵌入式采集。当前 `VideoSensor` 与 `SixCamSensor` 已通过 FIFO 启动 FFmpeg 并输出 `.mkv` 文件。

## 决策驱动因素

1. 在录制被意外中断时最大化已落盘视频的可恢复性。
2. 适配 MPP 裸 H.265 输出与 FIFO 的持续流式写入路径。
3. 保留视频轨道的时间戳和容器元数据，避免由应用自行管理裸流 PTS。
4. 保持 FFmpeg、VLC 与 ffplay 等板端和离线工具的兼容性。
5. 将浏览器、QuickTime 或 iOS 等对 MP4 的兼容性需求与采集主路径解耦。

## 候选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 将 FIFO 中的 H.265 直接保存为裸流 | 结构简单，异常中断后已写入 NAL 单元通常仍可取得 | 无时间戳、索引和轨道元数据；不便直接播放，音视频同步需由应用额外处理 |
| 封装为 MP4 | 浏览器和部分消费端兼容性较好 | 常规非碎片化写入在未完成 `moov` 索引时中断，文件可能无法直接播放或需要修复；不适合作为默认嵌入式录制格式 |
| 封装为 MKV | 适合持续流式写入，保留时间戳与轨道信息；断流后已写入的 Cluster 仍可使用 | 浏览器和 QuickTime 的原生支持较弱 |

## 决策

统一采集的 H.265 最终视频文件使用 FFmpeg 从 FIFO 直接封装为 MKV；MKV 是 session 内视频的最终归档形态。裸 H.265 仅作为 MPP 到 FFmpeg 之间的瞬态中间流，不作为 session 的最终归档文件。

## 理由

MKV 同时保留了裸流方案的顺序写入特性和容器方案的时间戳、轨道描述能力，最符合 RK3588 多路实时写盘的路径。关键原因是：MKV 持续落盘 Cluster，断流或异常停止时已写入的部分仍然可用；MP4 在最终 `moov` 索引尚未写入时中断则无法直接使用。相较于独立保存裸 H.265，MKV 不要求应用额外保存 PTS 或为回放自行构建索引。因此 MKV 是 session 的最终归档与后续处理输入，不以 MP4 替代。

## 实施约束

- `VideoSensor` 和 `SixCamSensor` 继续使用命名 FIFO 将 MPP 产生的 H.265 数据写入 FFmpeg。
- FFmpeg 以流拷贝方式（`-c copy`）输出 `.mkv`，不得在采集主路径进行视频重编码。
- session 内的视频文件名及 device-ui 的文件识别继续以 `.mkv` 为准。
- 不持久化单独的 `.h265` 裸流文件；需要帧级分析或其它编码器输入时，从 MKV 提取或增设明确的旁路输出。
- 若有外部系统仅接受 MP4，可由外部消费端从已归档的 MKV 派生副本；该副本不属于 session 的最终归档，也不得替代或删除原始 MKV。

## 正面后果

- 采集流程可持续将 H.265 写入 FIFO 并由 FFmpeg 直接封装，不需要应用承担容器索引管理。
- 每路视频得到带时间戳和轨道信息的可播放文件，便于 ffprobe、ffplay 和后续处理。
- 断流、断电或进程异常停止后，已写入的 MKV Cluster 仍可读取和播放，不会像未完成索引的 MP4 一样整体不可用。
- 裸 H.265 不再作为最终文件，避免 session 出现缺少回放元数据的中间产物。

## 负面后果

- `.mkv` 在浏览器、QuickTime 和部分移动端播放器上的原生兼容性不如 MP4。
- 每路视频需要维护 FIFO 和一个 FFmpeg 子进程，增加进程管理与故障观测需求。

## 风险

| 风险 | 触发信号 | 缓解措施 |
|------|----------|----------|
| 部分播放器不支持异常停止的 MKV 索引状态 | 特定播放器不能准确定位或显示时长 | 使用 FFmpeg、ffprobe 与 ffplay 作为采集数据的标准读取工具，并在板端验证 |
| FFmpeg 子进程异常退出 | 日志出现非零退出码，FIFO 写入失败 | 记录退出状态；停止 session 并保留已生成文件供恢复；将重试策略作为独立运行时设计评估 |
| 下游要求 MP4 直接播放 | 浏览器或客户端无法播放 MKV | 保留 MKV 作为最终归档；由外部消费端派生 MP4 副本，不改变 session 格式 |

## 回退方案

仅当未来出现新的、经过验证的最终归档格式能同时满足“断流后已写入数据仍可用”和多路实时写盘要求时，才可新建 ADR 评估替代方案。外部系统需要 MP4 并不是切换 session 格式的回退条件：应始终保留 MKV 归档，并由外部消费端生成 MP4 副本。

## 验证方式

| 验证项 | 操作或指标 | 通过标准 | 状态 |
|--------|------------|----------|------|
| 正常录制可识别 | 对每路 `.mkv` 执行 `ffprobe -show_streams -show_format` | 可识别 H.265 视频流、分辨率、帧率和容器信息 | 已定义 |
| FIFO 流拷贝 | 检查 FFmpeg 参数与日志 | 输入为 FIFO H.265，输出为 `.mkv`，且没有重新编码日志 | 已定义 |
| 异常中断恢复 | 在 RK3588 录制过程中断电或终止采集进程后执行 `ffprobe`/`ffplay` | 已写入的 MKV Cluster 可被读取和播放 | 已定义 |
| 最终归档格式 | 检查 session 输出目录和文件清单 | H.265 视频只以 `.mkv` 作为最终归档文件；不存在以 MP4 替代 MKV 的流程 | 已定义 |
