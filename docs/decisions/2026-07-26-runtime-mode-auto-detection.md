## 背景

unified_capture 与旧 stereo daemon、guidaview 共享同一组 USB 设备，不能同时运行。device-ui 后端需要知道当前应调用哪套控制链路，同时状态接口每约 3 秒轮询一次，不能为每个请求进行冗余探测。

## 决策驱动因素

1. 避免要求现场人员手工切换配置。
2. 运行模式必须基于服务实际可响应状态，而不仅是 Socket 文件存在。
3. 高频 API 轮询不应持续创建额外探测负载。
4. unified_capture 不可达时必须保留旧链路。

## 候选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 静态配置选择模式 | 行为明确，探测成本为零 | 部署和现场切换容易配置错误 |
| 只判断 Socket 文件存在 | 实现简单 | 残留 Socket 不能证明服务可用 |
| 发送 `status` 自动探测并缓存 3 秒 | 判断真实可用性，减少重复请求 | 切换识别最多延迟约 3 秒 |

## 决策

device-ui 后端通过连接 `/tmp/unified_capture.sock` 并发送 `status` 自动识别 unified_capture；探测结果缓存 3 秒，未得到有效响应时使用旧 stereo/guidaview 链路。

## 理由

主动 `status` 探测同时验证 Socket 和服务协议可用性，比文件存在检查可靠。3 秒缓存与前端轮询周期相当，在降低连接开销的同时保持可接受的模式切换延迟。

## 实施约束

- 探测命令超时为 2 秒，异常统一视为 inactive。
- 缓存同时保存时间戳与布尔状态。
- 所有需要选择后端的 API 通过同一 `captureActive()` 判断。
- 不允许两套采集服务同时占用设备。
- 服务重启窗口内允许暂时回退或返回不可达，调用方应重试。

## 正面后果

- 无需额外部署开关。
- 检测依据是服务真实响应而非文件状态。
- 高频状态请求共享缓存，降低 Unix Socket 探测次数。
- 保留旧系统兼容路径。

## 负面后果

- 模式变化可能在 3 秒缓存期内暂未被识别。
- 服务短暂抖动可能使一次缓存周期选择旧链路。
- 自动模式比显式配置更依赖清晰的优先级规则。

## 风险

| 风险 | 触发信号 | 缓解措施 |
|------|----------|----------|
| 缓存过期前路由错误 | 服务刚启动或刚退出 | 将缓存限制为 3 秒并允许 API 重试 |
| 两套服务同时运行 | USB 设备占用或控制冲突 | 部署脚本和 systemd 保证互斥 |
| 残留 Socket | connect 或 status 超时 | 以有效 JSON 响应作为 active 条件 |

## 回退方案

若自动探测在现场产生不可接受的模式抖动，可增加显式配置作为最高优先级，并将自动探测保留为默认或 `auto` 模式。

## 验证方式

| 验证项 | 操作或指标 | 通过标准 | 状态 |
|--------|------------|----------|------|
| active 探测 | unified_capture 运行时发送 status | 返回有效响应并选择新链路 | 已通过 |
| inactive 回退 | 停止 unified_capture | 选择旧链路 | 代码已实现 |
| 缓存 | 3 秒内重复调用 | 不重复执行底层探测 | 代码已实现 |
