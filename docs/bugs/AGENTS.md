# Bug 文档编写规则

本文件适用于 `docs/bugs/` 及其所有子目录。Codex 在本目录创建、迁移、修改或审查 Bug 文档时，必须遵守以下规则。

## 创建前

1. 先阅读本文件、`README.md` 和 `TEMPLATE.md`。
2. 搜索已有记录，避免同一问题重复建档：

   ```bash
   rg -n "<设备名|错误码|关键日志|模块名>" docs/bugs
   ```

3. 默认新建独立文件；只有同一根因、同一复现链路的一组症状才合并记录。

## 文件命名

- 实际 Bug 文件必须命名为 `YYYY-MM-DD-<slug>.md`。
- 日期使用首次确认或首次记录日期。
- `<slug>` 使用小写英文和连字符，描述模块与故障，例如：
  `2026-07-25-pthread-socket-tstc-mpp-crash.md`。
- `README.md`、`TEMPLATE.md` 和 `AGENTS.md` 不受日期命名规则约束。

## 内容结构

以 `TEMPLATE.md` 为唯一基础模板，不删除以下二级标题，也不改变顺序：

1. `元数据`
2. `现象`
3. `影响`
4. `环境`
5. `复现步骤`
6. `预期结果`
7. `实际结果`
8. `证据`
9. `根因分析`
10. `解决或规避方案`
11. `验证结果`
12. `相关文件`
13. `经验教训`
14. `变更记录`

写法参考 `../2026-07-23-stage-test-plan.md`：

- 标题直接说明模块和故障。
- 顶部元数据明确状态、严重级别、日期和负责人。
- 每个复现步骤同时写清“操作”和“预期”。
- 命令、代码和日志使用带语言标识的代码块。
- 多组实验结果优先使用 Markdown 表格。
- 用 `---` 分隔元数据与正文。

## 证据约束

- 只记录实际观察到的日志、命令、提交、实验结果和文件路径。
- 不猜测设备型号、SDK 版本、返回值、发生频率或验证结论。
- 未确认的根因标为 `待确认` 或 `推测`，并写出确认它所需的实验。
- 修复尚未在目标硬件验证时，`验证结果` 必须写 `未验证`，不得写“已解决”。
- 引用日志时保留关键上下文；涉及密钥、账号、客户数据时先脱敏。
- 修改已有记录时，在 `变更记录` 追加日期和修改摘要，不覆盖历史结论。

## 完成前检查

对所有实际 Bug 文件执行：

```bash
for file in docs/bugs/20*.md; do
  for heading in "## 元数据" "## 现象" "## 影响" "## 环境" \
    "## 复现步骤" "## 预期结果" "## 实际结果" "## 证据" \
    "## 根因分析" "## 解决或规避方案" "## 验证结果" \
    "## 相关文件" "## 经验教训" "## 变更记录"; do
    grep -Fq "$heading" "$file" || {
      echo "缺少章节: $file -> $heading"
      exit 1
    }
  done
done
```

然后执行：

```bash
git diff --check
```

只有两项检查均通过，才可声称 Bug 文档完成。
