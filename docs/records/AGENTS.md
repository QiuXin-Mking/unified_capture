# 执行记录编写规则

本文件适用于 `docs/records/` 及其所有子目录。Codex 在本目录创建、迁移、修改或审查测试计划、集成记录和执行报告时，必须遵守以下规则。

## 文件命名与分类

- 实际记录命名为 `YYYY-MM-DD-<slug>.md`。
- 日期使用执行开始或首次记录日期。
- `<slug>` 使用小写英文和连字符。
- 测试计划记录“准备如何验证”；集成记录记录“实施了什么”；执行报告记录“实际运行结果”。
- 架构选择提取到 `../decisions/`，故障闭环写入 `../bugs/`，不要在 record 中重复维护多个事实版本。

## 内容要求

新记录以 `TEMPLATE.md` 为基础，并包含：

1. `元数据`
2. `提取的 ADR`
3. `目标`
4. `范围`
5. `环境`
6. `执行步骤`
7. `预期结果`
8. `实际结果`
9. `问题与处理`
10. `结论`
11. `后续事项`
12. `相关文件`
13. `变更记录`

迁移历史记录时不得为了套模板而删除有效内容。可以保留原有章节体系，但必须在顶部补充元数据和“提取的 ADR”，并确保目标、步骤、结果和后续事项仍可识别。

## 证据与 ADR 提取

- 命令、日志、API 响应和实验数据保持原样并脱敏。
- 明确区分“预期”和“实际”，未执行项标记为未验证。
- 出现可独立撤销或替换的技术选择时，在 `../decisions/` 创建 ADR。
- 算法参数和同一方案的实现细节归入一个 ADR，不拆成多个参数 ADR。
- record 与 ADR 使用相对链接双向关联。
- Bug 表格可作为实施记录的一部分，但完整故障闭环应链接 `../bugs/`。

## 完成前检查

1. 文件名符合日期格式。
2. 顶部包含“提取的 ADR”。
3. 所有相对链接目标存在。
4. `git diff --check` 无输出。
